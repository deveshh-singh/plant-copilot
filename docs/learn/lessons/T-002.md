# T-002 — Databricks bundle and setup job: what you just built

## In plain words
Your laptop can now push the project's code to Databricks and run it there with three
commands. The first job it ran made the "folders" (schemas and a volume) your sensor data
lives in, and the NASA files are now uploaded into that volume.

## The idea behind it
- **Asset Bundle** (`databricks.yml`): a recipe that says "these jobs, this code, this
  workspace". Like a `docker-compose.yml` for Databricks: the workspace is rebuilt from the
  file, not from clicks in the browser, so it is repeatable and reviewed in git.
- **OAuth login (U2M)**: you logged in once in the browser; the CLI keeps a short-lived
  token in its own cache. Nothing secret is in the repo. The profile name `plant-copilot` is the key.
- **Serverless**: no cluster to size or start; Databricks supplies compute per run. That is
  why the job file has no `new_cluster` block.
- **Unity Catalog names** have three parts: `catalog.schema.object` → `workspace.plant_bronze.raw`.
  A **volume** is a governed folder for files (our `.txt` files); tables come next, in M1.
- Why a notebook creates the schemas instead of the bundle: in development mode the bundle
  renames what it creates (`dev_<you>_...`), and our pipeline needs fixed names.

## Where it lives
```yaml
targets:
  dev:
    mode: development          # ← safe sandbox: prefixes job names, pauses schedules
    default: true              # ← `-t dev` is the default
    workspace:
      host: https://dbc-8b90102c-1331.cloud.databricks.com
      profile: plant-copilot   # ← which saved login to use
```
File: `databricks.yml` · and `notebooks/00_setup.py`:
```python
spark.sql(f"CREATE SCHEMA IF NOT EXISTS {CATALOG}.{schema}")  # ← safe to re-run
spark.sql(f"CREATE VOLUME IF NOT EXISTS {VOLUME}")
```
